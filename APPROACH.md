# MigrateFlow Approach

MigrateFlow treats employee migration as a supervised data system, not an autonomous chatbot. The backend owns deterministic ingestion, evidence scoring, policy, cleanup, validation, retry, idempotency, and rollback. A local open-source Ollama model is limited to semantic mapping proposals and concise explanations. React gives a consultant one place to upload sources, follow progress, resolve ambiguity, inspect transformations, and control external effects.

The workflow begins with bounded CSV and XLSX ingestion. Each file is stored under a generated batch ID outside public paths. Profiles capture types, null and uniqueness ratios, date patterns, duplicate counts, identifier evidence, and a few masked examples. Prompt-like cell text is treated as untrusted data and redacted before model context. Raw datasets never enter model prompts.

Mapping confidence is calculated in code from normalized name similarity, curated aliases, type compatibility, value patterns, uniqueness, and a bounded structured model proposal. Each component remains inspectable. A SQL-backed state machine owns the running durable pause-and-resume flow; a tested LangGraph contract captures the intended policy/interrupt topology without becoming a second source of truth. The policy gate auto-applies only scores of at least 0.90 with compatible types, no collision, and no policy warning. Lower confidence, target collisions, ambiguous dates, disputed required fields, and conflicting identifiers create an escalation with Approve, Correct, and Reject actions.

Cleaning uses reversible deterministic rules: Unicode normalization, trimming, email lowercase, configured phone normalization, explicit name casing, empty-to-null conversion, and unambiguous ISO date conversion. Missing required identifiers are never invented. Every field change records the before and after values, rule, confidence, actor, time, and reason. Exact duplicates can merge with source provenance; conflicting probable duplicates remain separate and escalate. Validation runs twice at most before human review.

Approved valid records reach a separate mock target through an idempotency key and canonical payload hash. Identical retries return the prior result; reusing a key with a changed payload conflicts. Only retryable failures retry, retry counts are bounded, and rollback compensates only records created by the selected batch. Material actions generate append-only audit events and safe SSE updates.

The primary tradeoff is precision over automation. Conservative escalation can increase reviewer workload, but it prevents ambiguous dates, identity conflicts, and low-confidence mappings from silently changing employee data. SQLite, a compact evaluation set, and a mock connector keep the prototype reviewable but are not production scaling choices. Next steps would add Alembic migrations, client-specific target adapters, richer evaluation distributions, role-based access, encrypted object storage, background workers, and operational dashboards without weakening the existing authority boundary.
